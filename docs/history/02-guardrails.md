# 02 — 守门层就位（2026-10-24 早，7.0 – 7.5）

## 目标

6.1 拿到 29%，说明方向对但不够稳。这一阶段的主题是：**把「为什么失败」变成可检测的信号。**

## 四层守门

### 1. 离線评分（daemon 常驻）

前面已有。这一阶段补上的是**早停策略**：

```
候选逐个生成，每生成一个就评分；一旦有候选落在可交付区就停，不再浪费算力。
```

**第 16 課**是这里踩的坑：

> 早停不看 gen 会系统性错过星级候选（六轮一键中 3 个候选就停、星级全在第 3–4 位之后）。
> `shouldStopEarly` 加 `genGate` 后首发 0.020 直落 0% AI。

也就是说：早停的判据不能只看「CV 够不够」，还要看「gen 够不够低」。
否则会在一个语法漂亮但 AI 味重的候选上停车。

### 2. 语法手术（surgicalRepair）

候选里总会有几句语法崩坏的。早期做法是整段重生，成本高且会破坏上下文。

改进：**只对受伤句做局部重生**，其余不动。

```text
逐句算 CoLA → 低于阈值的句子单独送模型重生 → NLI 守门确认没改意思 → 替换
```

### 3. NLI 守门

段落重组 X 是按段落择优拼出来的，容易在接缝处产生矛盾或信息丢失。

NLI（自然语言推断）用来检查：
- 重组后的段落与原句是否矛盾（contradiction）
- 是否丢了原句的信息（entailment 不足）

**这是「否决制」的雏形**——不是保证改得好，而是保证坏的不出去。

### 4. LT 确定性语法层

LanguageTool 6.8（本地 JRE）处理拼写、标点、少量语法规则。

当时的关键判断是：**LT 是安全层，因为它不改句式。**

这一点在 10.0 被重新验证了一次（见 09-lessons 第 14 課的延伸）：

> LT 確定性語法層不改變 Turnitin 結果（H4 <20% 複現 H2）。
> 兩次 <20% 的共同配方：hz 多候選擇優 + 手術 + 零 API 潤飾；
> damage 只要 0.02–0.06 也可通過。

## 首次 <20%

| 文档 | 版本 | Turnitin |
|---|---|---|
| H2（叙事） | 7.x | **1%**（not surfaced） |
| H4（生产 A + LT） | 7.x | **3%**（not surfaced） |

这是第一次稳定进入 <20% 区间。

**但这里埋了一个坑**：H4 的 `<20% (not surfaced)` 是「低于阈值不显示」，
不是具体数字。后来证明这种「不知道具体多少」的模糊状态会让人过度乐观。

## 红区首战：E2 0% 与 R3 的失败（7.4 – 7.5）

### E2 成功

E2 议论文（原稿 gen 0.232）在 **7.5** 拿到 **0%**——用**一个**码（`F20A277274`）。

> 补充：7.x 阶段总共花了 3 个码（H2、H4、E2-grind 各一），不是 E2 一单用了 3 个。

用的新武器是 **grind（段级研磨）** 和 **数字斗篷（cloakNumbers）**：
- 研磨：对整段反复重生，直到整份分数改善且伤率在带内
- 斗篷：把数字换成 `ZXQ0K` 占位符，模型看不到就不会丢

### R3 失败

同一时期跑红区报告 R3（原稿 gen 0.96+），语域段卡在 0.168，上不去。

**当时的误读**：以为是「研磨参数待调」，继续加轮数、调阈值。

**真实原因**（到 8.10 才确认）：这是引擎分布天花板，不是参数问题。
R3 的语域段对 hz 12B 来说根本生成不出来。

> 第一次误读：把「能力边界」读成「参数未调」。

## 这一阶段的教训

1. 守门层（评分/手术/NLI/LT）必须齐全，否则无法定位失败原因。
2. 早停判据要双指标（CV + gen），单指标会系统性错过好候选。
3. LT 安全的原因是它不改句式——这条在 10.0 成了 `l2_fix.py` 的设计原则。
4. **`<20% (not surfaced)` 不等于「很好」**，只等于「低于显示阈值」。这个模糊性后来导致了误读。
