# 01 — 起源：从「润饰文本」到「选择式管线」（2026-10-23）

## 起点

最初的假设很简单：**给 hz 一段 AI 写得不太好的文字，它会改得更像人写的。**

第一份测试文档是糖税议论文（E2），原稿 `gen 0.232`——有人类底子的稿子，只是被 AI 润过。
第一次跑，Turnitin 给了 **59%**。

这个数字成了整条管线的起点，因为它否证了最朴素的想法：**单次改写不够**。

## 尝试一：多跑几次挑最好的（2.0 → 6.1）

既然单次结果不稳，那就多跑几次、挑一个最好的。

结果：

| 版本 | 策略 | Turnitin |
|---|---|---|
| 2.0 | 单次改写 | 59% |
| ~4.0 | 多候选取最优 | 25% |
| 6.1 | 多候选 + 手术 | **29%** |

25% 与 29% 说明多候选有效，但收益不稳定——而且 6.1 明明零语法伤（damage 0.000），
分数却比 5.0（damage 0.086）还差。

这就是**第 11 課**的来源：

> 纯 hz 管线（无 API 润饰）+ 7 次手术后 damage 0.059 → Turnitin <20%。
> 对比 final6.1（零 damage + API 润饰）= 29%：
> **润饰度每升一级，Turnitin 约 +10–15%。**

## 关键发现：润饰是毒药

当时的直觉是反的。以为「语法越干净，越像好学生，越安全」。
实际观测正好相反：**越干净越像 AI**。

校準集第 6、7 课把这一点钉死：

> 第 6 課：V2(0%) vs V3(24%) 十一分钟对照，隔离出单一变量：散文润饰度。
> 粗糙版（碎片、错介词、重复、缩写）→ **0%**；润饰版 → **24%**。
>
> 第 7 課：跨两个文档族、11 个点的一致定律：**润饰度 ↑ → Turnitin ↑**。
> 交付甜点 = 语法安全但保留可见的人类不完美。

这条定律在 10.0 里仍然有效——它是 `l2_fix.py` 只修「读者可见硬伤」、
不碰句式与用词的根本理由。

## 离線评分器登场

靠 Turnitin 迭代太贵（每个码都是钱），所以需要一个便宜的替代品。

方案：常驻 daemon，计算四个离线指标——
- **CoLA**（语法可接受度，句级）
- **tmr**（AI 文本分类器）
- **EditLens**（AI 修訂 delta）
- **perplexity**（困惑度）

每次评分 0.01–数秒。一次 run 可以做上百次评分，成本≈电费。

**但第 1 課立刻打了预防针**：

> tmr/EditLens/perplexity 无法解释 5.0(<20) vs 6.0(56%)——
> **离线检测器在 hz 输出之间失去鉴别力。**

这句话后来变成了整个项目的核心纪律：
**离線评分是守门员，不是预言家。** 它能挡住已知失败模式，但不预测绝对分数。

## 6.1 的结构：选择式管线成形

到 6.1，管线的骨架已经是今天的样子：

```text
原稿 → plan（分段/分单元）→ K 候選（多温度采样）→ 离線评分
     → 语法手术（受伤句重生）→ 段落重组 X → NLI 守门 → LT 语法层 → 交付
```

关键设计：
- **候选池 + 择优**，而不是「改一次就交」
- **段落重组 X**：不只用单个候选，而是逐段从不同候选里挑最好的
- **NLI 守门**：防止改写出语义矛盾

## 这一阶段的教训

1. 单次改写不够，多候选择优是必需的。
2. 润饰与检测分数反相关——这是反直觉的，也是后面所有设计的锚点。
3. 离線指标只能做相对导航，不能承诺绝对分数。
4. **实测通过 ≠ 整体成功**——6.1 零语法伤却拿 29%，说明「指标全绿」不等于「可以交」。

第 4 条当时没被真正吸收，后面还会再犯两次。
