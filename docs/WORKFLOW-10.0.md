## 2. L0 路由層（升級）

### 2.1 四語域特徵（零模型，<5ms）

```
p1_rate       第一人稱密度（I/my/me/we/our 每百詞）
cite_num_rate 內文引用 + 數字 / 段落數
nom_rate      名詞化詞尾（-tion/-ment/-ity/-ance/-ence/-sion）每百詞
mean_para_words 段落平均詞數
```

### 2.2 分診規則（3/3 驗證通過）

```python
if p1_rate >= 2.0:
    register = "student"            # 個人敘事 / 反思 / L2 作文
elif p1_rate < 1.0 and (nom_rate >= 3.5 or mean_para_words >= 120):
    register = "academic"           # 正式議論文 / 報告
else:
    register = "mixed"              # 中間帶
```

驗證樣本：

|---|---|---|---|---|---|

| E2-oneclick82 | 0.92 | 4.43 | 60 | academic ✓ | 0% AI |
| PELIC | 5.31 | 2.46 | 101 | student ✓ | 學生語域 |

## 3. L2 並聯生成層（核心變更）

### 3.1 候選配置

| 路徑 | Cand 1–3 | Cand 4–5 | Cand 6 |
|---|---|---|---|
| α（student） | B 三溫度（0.90/1.00/1.05） | A 兩次 | — |
| β（academic） | B 三溫度 | A 一次（膨脹小、可作長度備援） | — |
| γ（mixed） | B 兩次 | A 三次 | B→A 一次 |

### 3.2 顯存調度鐵律

**禁止逐句切換模型。** 批次執行：

```
Stage 1：載入 B（8.9 GB）→ 整篇所有段落跑完 3 個候選
Stage 2：卸載 B，載入 A（6.5 GB）→ 整篇所有段落跑完 2 個候選
```

600 字文稿只切換一次模型，切換開銷約 3 秒。

### 3.3 B 的長度控制（不靠 prompt）

實測：B 在長段落膨脹 1.22–1.36，且在 prompt 加字數指令完全無效（模型不聽）。

**解法：在 `assembleCrossover` 的字數懲罰項**

```python
score(p, c) = w1 * (1 - gen[p][c])
            + w2 * ppl_norm[p][c]
            - w3 * max(0, 0.42 - cv_global[c])          # CV 保底（新族門檻）
            - w4 * max(0, len_ratio[p][c] - 1.12)       # 段落膨脹懲罰
```

效果：B 膨脹 36% 的段落自動輸給 A 膨脹 5% 的段落，全篇膨脹率自然落在 10–12%。

## 4. L2.5 確定性修復層（新增，順序不能變）

```text
① L2 語法規則庫     純正則/詞典，修主謂一致、冠詞、可數性、代詞
② 確定性縮寫展開    學術區：don't→do not（學生區則保留）
③ LanguageTool 6.8  拼寫、剩餘標點（safe categories）
④ 字數預算          刪除優先，目標 ≤ 原文 1.12
```

### 4.1 為什麼順序不能變

- 語法規則先跑：修主謂一致會改變詞形，之後 LT 不會再誤判
- 縮寫展開在語法後：避免 `don't` → `do not` 影響主謂判斷
- LT 在最後：它是補充，不是主力（實測只覆蓋 4/15）
- 字數預算最後：前面所有修復都會微調詞數

### 4.2 L2 語法規則庫（起步 15 條，全部實測有效）

| 類型 | 規則示例 | 來源 |
|---|---|---|
| 可數性 | `make purchase` → `make purchases` | NUCLE 型 |
| 主謂一致 | `Physical store need` → `Physical stores need` | NUCLE 型 |
| 單複數 | `One of the major difference` → `differences` | PELIC 型 |
| 冠詞/複數 | `e-commerce platform has` → `e-commerce platforms have` | NUCLE 型 |
| 量化詞 | `less customers` → `fewer customers` | LT 可覆蓋 |
| 代詞一致 | `consumers … he has purchased` → `they have purchased` | B 輸出型 |
| 冗餘 | `both two channels` → `both channels` | NUCLE 型 |
| 句首重複 | 連續兩句 `Thus…` → 第二句改 `Therefore,` | B 輸出型 |

**實測代價**：15 處全修，CV 0.472→0.474、ai_mk 0.12→0.12、句數不變。
即質量軸可獨立修復，不破壞分數軸。

## 5. L3 雙軌驗收（這次教訓的核心）

### 5.1 分數軸（否決制）

| 檢查 | 門檻 | 動作 |
|---|---|---|
| CV（全篇） | ≥ 0.42 | 不足 → 換候選 |
| ai_mk | ≤ 0.20 | 超標 → 換候選 |
| 數字/日期/單位 | 100% 保留 | 遺失 → 整段回退原稿 |
| 內文引用 | 100% 對齊 | 不一致 → 回退 |
| NLI 內容保持 | ≥ 0.85 | 不足 → 回退 |
| 段落結構 | 與原稿一致 | 變動 → 回退 |

### 5.2 質量軸（同樣是否決制）

| 檢查 | 門檻 | 動作 |
|---|---|---|
| 語法硬傷計數 | 0 | >0 → 規則庫補漏（不重生成） |
| 段落字數比 | ≤ 1.20 | 超標 → 字數預算壓回 |
| 全篇字數比 | ≤ 1.12 | 超標 → 刪除優先 |
| 縮寫率（學術區） | ≤ 0.20 | 超標 → 確定性展開 |
| 可讀性 | 句均詞 14–28 | 超範 → 換候選 |

**兩軸都過才交付。** 這是 WORKFLOW.md「三次誤讀」的直接修正：
分數軸通過 ≠ 交付成熟。

## 11. 離線整合測試結果（2026-10-29）

用 `pipeline/integrate10.mjs` 對 `highAI-0983` 的 3 個正文段（537 詞，原 CV 0.359）
跑完整 10.0 核心鏈（並聯生成 → 擇優 → 修復 → 雙軌驗收）：

| 階段 | 結果 |
|---|---|
| 並聯池（beta：routeb×3 + routea×1） | 4 個候選，71 秒 |
| `assembleCrossover` CV 提升 | CV 0.359 → **0.450**（目標 0.42，達標 ✓） |
| L2 修復 | 0 條規則觸發（該文本無 NUCLE 型錯誤） |
| 分數軸 | **PASS**（CV 0.450 ≥ 0.42） |
| 質量軸 | **FAIL** —— 字數比 **1.295**（上限 1.12） |

### 11.1 暴露的真問題：B 的系統性膨脹

所有 routeb 候選都膨脹 1.22–1.36，`assembleCrossover` 的 `lengthPenalty` 只能
在候選間選「相對最短」的，但當**全部候選都超標**時無法解決。

這不是候選選擇問題，是生成端特性：
- B 的訓練語料（NUCLE）段落較長（平均 270 詞），模型傾向擴寫
- 在 prompt 加字數指令實測無效（模型對額外指令不敏感）

### 11.2 因此 10.0 必須接上字數預算

第二次測試加入 `lengthConverge`（純選擇，不改文本：逐段換成更短的候選）：

| 版本 | 字數比 | 處置 |
|---|---|---|
| 僅 `lengthPenalty` | 1.295 | 只能選「相對最短」，全部超標時無效 |
| 加 `lengthConverge` | **1.204** | 換了 1 段，改善 7%，仍未達 1.12 |

結論：**候選池整體膨脹時，選擇無法解決，必須靠文本壓縮。**

`applyWordBudget`（管線第 5.9 步，刪除優先）是必需項：

```text
並聯擇優（CV 達標）→ lengthConverge（選短）→ wordBudget（刪冗餘）→ 複檢 CV
```

風險：壓縮會降低 CV。實測 CV 0.459 有 0.039 的餘裕（目標 0.42），
刪掉 45 詞約影響 CV 0.01–0.02，仍在安全區內。

**這是 10.0 目前唯一未閉合的環節**，下一步是把 `lengthConverge` 之後接上
`applyWordBudget`，並在壓縮後複檢 CV。

### 11.3 為什麼不能靠調 prompt 解決

實測（v9 簡報 §13.1）：在 B 的 prompt 後追加「保持原文長度」或明確句長配額，
模型完全不理會（要 6 句給 8 句），且膨脹反而增加。這是續寫模型的
「提示詞必須逐字一致」約束，不是參數問題。

### 12.2 結果

| 階段 | 結果 |
|---|---|
| plan | 6 段 6 unit，標題保護 p0，references 4 段保留 |
| 候選生成 | 4/6（早停），coverage 60–100% |
| 選定 | cand1（候選 3，routea） |
| **雙軌驗收** | CV **0.558**、gen 0.041、**語法硬傷 0**、字數比 **1.005**（551→554） |
| 結論 | **兩軸通過 ✓** |
| 交付 | `final8.0.docx` |
| **真碼（Turnitin）** | **AI 0%** / 查重 18%（Internet 10% + Publications 8%）/ **0 flags** |
| Submission ID | `trn:oid:::26334:318623574` |

### 12.3 但暴露了一個關鍵限制

**4 個候選全部被硬過濾淘汰**：

```
cand1 淘汰（CV=0.463 cvRatio=0.79 coverage=0.60）
cand2 淘汰（CV=0.465 cvRatio=0.79 coverage=0.80）
cand3 淘汰（CV=0.596 cvRatio=1.01 coverage=0.80）
cand4 淘汰（CV=0.591 cvRatio=1.01 coverage=1.00）  copy=0.86
```

最终走的是 `bandFallback`（降级交付），不是正常择优。

### 12.4 根因：两颗新引擎都不适合「已有人类底子」的文档

E2 原稿的 `gen` 已经是 **0.036**（本来就很少 AI 味），所以：

| 引擎 | 行为 | 后果 |
|---|---|---|
| **routeb** | 判定「已经像人写的」→ **原样返回** | `returned the original` → coverage 不足、**copy rate 0.79–0.86** |
| **routea** | 愿意改写，但**会丢引用** | `drops citation (Colchero et al., 2017)` → coverage 不足 |

两条路都触发硬过滤：
- `minCvRatio: 1.1`（新文 CV 必须达到原稿的 1.1 倍）
- `maxCopyRate: 0.6`（复制率上限）

### 12.5 这验证了 L0 路由的必要性

## 十三、更正：v12 简报把「已过关的成品稿」当成了原始草稿

### 13.1 事实核查结果

Argon 指出 §12 的输入 `e2-oneclick82.docx` 不是原始草稿。核实后确认无误：

| 来源 | 数据 |
|---|---|
| `calibration.json` 第 17 点（`E2-oneclick82`，code 05B0C1E1EB） | gen **0.034**、CV **0.582**、words **664**、Turnitin **0 AI / 16 similarity / 0 flags** |
| 本次输入的实测 | gen **0.036**、CV **0.582**、words **664** |

**完全吻合。** 这份文件是 8.2 版本已经加工完成、且已经拿过 0% AI 的成品稿，
不是 E2 的原始草稿（原始 E2 的 gen 是 **0.963**）。

### 13.2 这个错误解释了什么

| 现象 | 真正原因 |
|---|---|
| `routeb` 原样返回，copy 0.79–0.86 | 输入已经是人味稿，B 判定无需改动（同一机制在串联实验已确认） |
| 4 个候选全被淘汰 | 原稿 CV 已是 0.582，`minCvRatio 1.1` 要求输出 ≥0.640，不合理 |
| 查重 18% | 落在 E2 家族历史区间（13% / 16% / 22% / 22%）内，与管线无关 |

### 13.3 所以 §12 的结论要改成

**这次验证的是「10.0 后处理链不会破坏已过关文档」**（零负向回歸，
CV 0.582 → 0.558、gen 0.036 → 0.041、语法 0 硬伤、字数 1.005，Turnitin 仍 0%），
**不是「把高 AI 原稿压到 0%」**。

后者需要拿真正的 S4 原稿（`highAI-0983`，gen 0.983）跑，见 §14。

### 13.4 由此得到的过滤规则修正

`rankCandidates` 的硬过滤在「原稿已经很好」时会产生误杀：

```
origCv >= 0.45  →  取消 minCvRatio 1.1，改用绝对下限 cv >= 0.42
cand.gen <= 0.08 →  maxCopyRate 从 0.60 放宽到 0.88
```

理由：源文本已经够 bursty 时，要求输出再提升 10% 不合理；
候选已经够干净时，少改比乱改安全。

淘汰日志同时补印 `copyRate` 与 `gen`——它们是这次淘汰的主因却不在日志里。
